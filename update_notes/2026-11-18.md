# Update notes – 2026-11-18

## Leaving manipulation mode: pose not held (reported on a teammate's arm, stiffer XL330 variant)

### Fixes (firmware `lineform-ai.ino`)

- **No more library model-table dependence for position or mode.** Position is now read and written through the generic register access (`readControlTableItem(PRESENT_POSITION)` / `writeControlTableItem(GOAL_POSITION)`), via `readPresentRawDirect()` / `writeGoalRawDirect()`.
  - Before, `getPresentPosition()` / `setGoalPosition()` were used. Like `setGoalCurrent()` / `setGoalPWM()` before them (see 2026-11-11), these look the motor model up in the library's own range table first. For a model or library version it doesn't list, they fail silently or clamp to 0–4095. If the goal write in `holdHere()` failed, the motor turned on and **drove back to its old goal**: the hand-made shape was not held.
  - The direct access applies to every goal write: hold-here, the one-goal command (249), and the sync-write fallback.
- **Operating mode is set through the register and read back** (`setModeChecked()`: 5 = current-based position, fallback 3). It is only written if different. Before, a failed `setOperatingMode()` left the motor silently in its old mode.
- **`holdHere()` verifies the goal write** by reading it back, retrying up to 3×, and remembers the result.
- **New command 239 STATUS_HOLD** (`+ seq`). For each motor it returns: torque on ×10000 + goal write ok ×5000 + |present − hold goal| in 0.1° (capped at 499.9°).
- **Framing boundary lowered: headers ≥ 230, data < 230** (was 240) to make room for header 239. Data bytes never exceed 199. GUI (`SerialLink.pde`) and firmware (`HEADER_MIN`) changed together.

### Hold check (GUI `Modes.pde`)

About 1.5 s after switching back to AI mode, `modesVerifyHold()` asks the firmware (239) about every motor that should hold. If something's wrong, it reports it in the chat (and prints "Hold check: all N motors holding" to the console if everything's fine):
- **TORQUE OFF** on motor X: it didn't turn back on.
- **Goal could NOT be written** on motor X: it may have driven back to its old pose.
- **Drifted** > 5° on motor X: too weak or soft for the load, or pulled back to a joint limit.
- **Old firmware**: no ACKs, or no answer to 239.

### Tested (host harness, real firmware code, simulated motor registers)

- The library's `getPresentPosition` / `setGoalPosition` / `setOperatingMode` were made to fail. Setup still put the motors in mode 5. Hand poses were held exactly, and a pose past the 195° limit was held at the limit. The hold check reported torque on, goal ok, 0.0° deviation.
- Framing regression with the new boundary: sliced 251 and sliced 239 commands are dropped (NAK) and the next valid command runs; bad checksums are rejected; stray bytes are skipped.

### Other possible causes on a teammate's arm (not code bugs)

1. **Firmware not re-uploaded after pulling.** The GUI and firmware must be the same version. Old firmware doesn't know 241 / 239, and the hold check now says so.
2. **`local_config.h` doesn't match that arm.** With wrong offsets or reversed motors, joints read past −15/195 and are pulled back to the limit. Look for red `LIMIT` readouts in manipulation mode and the "Moved back inside the range" chat message.
3. **Rows switched OFF / at 0 % torque** stay limp by design (the chat says how many).
4. **Overload protection** tripping right after the motors re-engage switches back to manipulation mode (red warning box).

## Gains per motor MODEL (chains that mix XL330 variants)

**How it works.** Each motor reports its model number (register 0; e.g. XL330-M077 = 1190, XL330-M288 = 1200). In firmware `local_config.h`, `MODEL_GAINS_LIST` holds one gain set per model, and every motor automatically uses the set for its own model:

```c
//                 model  P L0   L1   L2   L3  I gain (L0)
#define MODEL_GAINS_LIST \
  {1190,  800, 700, 350, 120,  30},  /* XL330-M077 (soft) */ \
  {1200, 1200, 700, 350, 120, 150}   /* XL330-M288 (stiff) */
```

- A motor whose model has no entry uses `STIFFNESS_P_GAINS_LIST` / `DROOP_I_GAIN`, as before. Single-model arms and older configs work unchanged.
- `P_GAIN_PCT_LIST` is still a per-motor trim (%), now applied on top of that motor's model set.
- New `MOTOR_MODEL_OVERRIDE_LIST` (by motor number, 0 = what the motor reports) forces a motor onto another model's set, e.g. if its model can't be read.
- No other setting depends on the model: the torque bar is relative to each motor's own Current Limit, and speed limits mean the same on every model.
- **This arm:** one set `{1190, 800, 700, 350, 120, 30}` with the same values as the fallback, so behaviour is unchanged. `local_config.example.h` documents a mixed M077 + M288 example.

**Diagnostics.**
- New firmware commands **238** (model number per motor; +20000 = no set matched) and **237** (Position P Gain read back from the motor).
- The GUI's startup/Reset console table now has **model** and **P gain** columns. It prints a NOTE listing motors that have no `MODEL_GAINS_LIST` entry.
- Model names in the GUI (`motorModelName`): 1190 XL330-M077, 1200 XL330-M288, 1210/1220 XC330-T181/T288, 1230/1240 XC330-M181/M288. These are labels only; matching always uses the number the motor reports, so check the table if a name looks wrong.

**Tested (host harness, real firmware code).** Simulated chain: motors 1–4 report 1190, 5–8 report 1200, motor 9 reports 1230 (no set), motor 10's model is unreadable and overridden to 1190, with the example mixed config (CRLF, multi-line).
- Results: 1–4 → P 800 / I 30; 5–8 → P 1200 / I 150; 9 → defaults, flagged "no set"; 10 → P 800 / I 30.
- At level 2: P 350, I 0 for both models.
- Regressions passed: this arm's own config, hold-from-manipulation, and framing.

## Later the same day: teammate's stiffer arm

### Motor IDs 2–12 (firmware + GUI)

- The chain is now **Dynamixel IDs 2 (base) … 12 (tip)**. On the teammate's arm, assembled the other way round, ID 1 isn't connected.
  - Firmware: `DXL_IDS = {2 … 12}`.
  - GUI: row "Motor N" drives ID N (`hwId()`), and the labels show the real ID too (`displayId()`). This applies to bars, 3D blocks, warnings, and the console.
- **3D view:** the unconnected ID 1 motor is drawn first, as the fixed block at the base labelled **"1"**, followed by motors 2 … 12.
  - `PASSIVE_BLOCK_LABEL` in `Gui_3_0.pde`.
  - `"base_block_first": true` in this arm's `local_config.json` (it was false, a leftover from the old arm).
- `REVERSED_MOTORS_LIST` now takes **hardware IDs** (= the labels).
- The per-motor lists (`ANGLE_OFFSETS_DEG`, `P_GAIN_PCT_LIST`, `MOTOR_MODEL_OVERRIDE_LIST`) are in chain order: first entry = ID 2.

### This arm's `local_config.h` (clean start)

- `ACTIVE_MOTORS 11`, nothing reversed, all offsets 0. The old motor 2 (+14.6) and motor 3 (+40.2) offsets are removed. Recalibrate directions and offsets on this arm.
- **Stiffer gains:** XL330-M288 (1200) and the fallback use P **1800 / 1200 / 700 / 300** (levels 0–3), I 150. They were 1200 / 700 / 350 / 120. An M077 (1190) set is kept in case one is mixed in.

### Safety nets

- **Overload trip: unchanged.** At ≥95% for 2 readings it switches to manipulation mode automatically. Only its warning moved: it is now pinned in the bottom-left panel (see Warnings below). `"overload_trip_pct": 0` now turns it off (the value used to be clamped to 10–150).
- **Twitch detector: off** by default (`"twitch_guard": false` in `local_config.json`). It no longer softens a motor or switches it off on its own. The motors' own hardware overload protection still works, and Reset still restarts motors that shut down.

### Hand moves in AI mode: lenient thresholds

- `"hand_move_threshold_deg": 2` (was 5; the code default is now 2 as well) and `"hand_move_confirm_readings": 1`. A push of more than 2° away from where the motor settled counts as a hand move after one reading.
- Once you let go, the motor holds the new angle and its bar takes it. Gravity sag is still accepted as the rest point first; with the stiff gains it is small.
- (`local_config.json` also has `"follow_hand_moves": true`. It should stay true.)

### Warnings: one panel, bottom-left, never in the AI chat

- New tab **`Notices.pde`**. Every motor / mode warning and status message goes to a "WARNINGS & STATUS" panel in the bottom-left corner, below the fit-quality info box. These include Reset check, hold check, manipulation/AI mode switches, joints moved back inside the range, Save Shape, twitch, and "manipulation mode is on" refusals.
- `chatAdd("error", …)` is routed there too, so **no error ever lands in the chat**. The chat holds only the conversation with the agents, plus their fit-quality / torque / stiffness notes.
- When the overload trip fires, its warning is **pinned** at the top of the same panel until you return to AI mode. It is no longer drawn under the manipulation banner.
- Status notices fade after 15 s and errors after 90 s; at most 4 are kept. Click the panel to clear it.

### White load line on every bar

The white line (live torque use, 0–100% of the motor's Current Limit) and "now NN%" are now drawn on **ANGLE, TORQUE and STIFF** bars of every active row, not only on TORQUE bars. They are not drawn in manipulation mode, where the motors are limp.

### Agents set angles, torque AND stiffness

Both agents now control all three per-joint settings and are told what they mean on this arm.

| | Designer (Shape mode) | Motion agent (Animate mode) |
|---|---|---|
| angles | segments (as before) | poses / traveling_wave (as before) |
| `joint_torque` 0–100 | yes (as before), stays after the shape | yes (as before), only while it plays |
| `joint_stiffness` level 0–3 | **new**, stays after the shape | yes, only while it plays |
| field left out | keeps the current values | keeps the current values (**was:** omitted stiffness = all full) |

- **Stopping an animation** now restores the stiffness levels from before it, like the torque. Before, every joint snapped back to full. Reset still sets everything to full / 100%.
- **The arm-state note** at the end of every user message now always lists each joint's current torque %, stiffness level, and any joints switched OFF, base to tip. Joint 1 = motor labelled 2. Before, torque was only mentioned when a joint was below 100%, and stiffness never. So the agents see what you set on the TORQUE / STIFF bars.
- The Designer's stiffness plan is handed to the Motion agent with the shape, like its torque plan.
- The chat shows "Designer set stiffness …" / "Stiffness during this animation …" lines when an agent changes it.
