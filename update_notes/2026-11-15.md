# Update notes – 2026-11-15

## Manipulation mode

A wide two-half switch at the bottom-center of the GUI picks the mode. It is styled like the ANGLE/TORQUE switches: the left half is **AI MODE** in blue, the right half is **MANIPULATION** in amber. The active half is bright with a white outline and a ● marker; the other half is dimmed and brightens on hover. Click a half to select that mode. The switch is drawn by hand, not a ControlP5 toggle.

## Fix: hold-after-hand-move now works in TORQUE view

Rows switched to TORQUE view used to be skipped by the live-angle loop. A motor showing its torque bar never held a new hand-posed angle, and its hidden angle bar went stale, so the 3D view went stale too. If every row was in TORQUE view, angles weren't read at all. Now angles are always read, and every row runs the same display + hold logic whichever bar it shows.

**Manipulation mode**

- All active motors go torque OFF (one atomic write of `254 id 0`).
- The angle bars and the 3D view show the real angles on every reading (every ~60 ms instead of ~120 ms). The AI-mode filters are skipped: no 45° glitch filter, no hand-move threshold, no pending-value hold, no snap-to-goal.
- Every row shows its angle bar. The ANGLE/TORQUE and ON/OFF switches, Create Shape, and Reset are hidden, and the bars are locked.
- Chat requests, animations, and hinge stiffness taps are refused. As a safety net, `sendSerialBytes()` drops every command except reads (242–248, 250, 253) and torque-off.
- The AI chat panel is hidden: the panel, input, Send, New chat, Critic and Shape/Animate buttons. The camera can use that area, and the chat comes back unchanged in AI mode.
- Save Shape still works: pose the arm by hand, then save it. With the chat box hidden, the pose is saved as `hand pose YYYYMMDD-HHMMSS`; rename it in `shape_library.json` if you like.
- Warm amber/brown color set (`MANIP_*` in `Theme.pde`) and a banner over the 3D view.
- Any unsent bar values (e.g. an AI shape not yet sent with Create Shape) are dropped.

**Back to AI mode**

- Each motor holds the exact pose it was left in, at the ON/OFF state and torque % its row had before. Rows that were OFF or at 0% stay limp.
- Then the normal AI-mode hold logic takes over: it waits to settle, accepts gravity sag as the rest point, and only a real push moves the motor.

## Overload protection

- In AI mode, every powered motor's live torque use (the white line, % of its full-strength Current Limit) is checked about every 120 ms. This works whether the row shows its ANGLE or TORQUE bar, and also during animations and slider drags. Loads are now read every cycle in AI mode, not only when a TORQUE bar is visible.
- If any motor reaches **95%** for **2 readings in a row** (~0.25 s, so one noisy sample doesn't trip it), the GUI switches to manipulation mode and all torque goes OFF. A red warning box under the banner names the motor(s) and their load. The warning is also logged in the chat (visible again in AI mode) and the console. It clears when you switch back to AI mode.
- Rows switched OFF or at 0% torque are not checked.
- Tune in `local_config.json`: `"overload_trip_pct"` (default 95) and `"overload_confirm_readings"` (default 2; 1 = trip on the first reading).

## Reset checks and restarts every motor

- After Reset sends the straight pose, the GUI sends the new firmware command **240 CHECK_RECOVER** in a background thread. For each motor, the firmware checks:
  - Does it answer (ping, 3 tries)? If not, it reboots it and pings again.
  - Does it have a hardware error (overload, overheating, voltage…)? If so, it reboots it.
  - Is torque on? If not, it restarts the motor with `holdHere()`: goal = present position, then torque on at its torque %.
  - It then verifies torque is on and the error is cleared.
- The firmware returns one result code per motor. The GUI posts a summary in the chat, e.g. "restarted motor 4 (overload error - rebooted), motor 7 (torque was OFF)", or "PROBLEM: motor 9 NOT ANSWERING - check its power and cable".
- If anything was restarted, the Reset pose is sent again so the restarted motors straighten with the others. The console diagnostics table follows, as before.
- Motors at 0% torque are left limp on purpose.

## Serial link: no overflow, no sliced-byte bugs

**Problem.** Commands were raw bytes with no pacing. A burst (e.g. Stop Animation: stiffness + torque for every motor) could arrive faster than the Arduino executes it, because each torque-on is several bus writes, or more with a reboot. If the input buffer overflowed, a lost byte shifted every byte after it, and e.g. a stray `0` read as a torque % switched a motor off.

**Framing.** Every command is now `<header ≥240> <data, each <240> <checksum = (header+data) & 0x7F>`.
- If the firmware finds a byte ≥240 where data or the checksum should be, the command lost bytes. It drops the command and treats that byte as the next header.
- A wrong checksum drops the command too.
- Stray bytes are skipped until the next header.

**Flow control (the speed limit).** Commands without a reply (255, 254, 252, 251, 249, 241) are answered with **ACK `0x06`** after they are fully executed, or **NAK `0x15`** if they were dropped.
- The GUI (`SerialLink.pde`, called from `sendSerialBytes`) waits for the ACK before sending anything else, so only one command is ever in flight. Bursts simply take a little longer.
- A NAK'd command is resent once.
- Reads (250, 248, 253, 242–247, 240) are paced by their own replies, as before.
- If the firmware never ACKs (old firmware), the GUI warns once in the console and falls back to a fixed 20 ms gap between commands.
- The firmware no longer skips ahead to the newest queued animation frame. With flow control there is never a backlog.

**Diagnostics.** The console's FIRMWARE line now shows dropped (damaged) commands, stray bytes, and the GUI's NAK / ACK-timeout counts.

**Tested** with a host harness around the real `loop()`: valid commands → ACK. A sliced 251 followed by a valid 254 → NAK, then the 254 runs. A bad checksum → NAK, nothing runs. Stray bytes are skipped. A sliced 255 frame followed by a valid 249 → NAK, then the 249 runs.

## Firmware

- New command **241 HOLD_HERE** (`+ id + percent`). It sets the goal to the motor's raw (multi-turn) present position, then turns torque on via `enableMotor()`. There is no 1.44° angle-byte rounding and no 60–310° clamp. A motor in an error state is rebooted first. Percent 0 means torque off.
- New command **240 CHECK_RECOVER** (`+ seq`). It returns a framed reply of 11 × (code·1000 + hardware error bits). Codes: 0 ok, 1 torque was off → restarted, 2 hardware error → rebooted + restarted, 3 not answering → rebooted + restarted, 4 still not answering, 5 restart failed, 6 limp at 0% on purpose, -1 not fitted.
- **Re-upload `lineform-ai.ino`.** With the old firmware, leaving manipulation mode leaves the motors limp.
